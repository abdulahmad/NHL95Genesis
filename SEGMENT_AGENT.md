# NHL 95 segment agent

This file is the queue. Do not rewrite it as a whole file. Edit the current row in place. Do not append a history entry.

## Current rules (Oct 2026; these override older notes below)

Naming lineage is 92G -> 93G -> 94G -> 95G, and the SNES ports sit beside their Genesis parents (93S from 92G/93G, 94S from 93S plus the 94G features).
- A routine, variable or table that matches its parent takes the parent's name. 92G is the naming root.
- Clash rule: if one name would mean two different things, the earliest game's meaning keeps the name and the later one gets a new name.
- Fix the earliest repo first, then propagate the change down the lineage (92 -> 93 -> 94 -> 95, and to the SNES repos).
- Team names: 93 uses the city names of its own data; 94 and 95 use NYI / NYR style abbreviations (team nicknames are not in the repo).

Source style:
- No rename-history, provenance or origin-tag comments ("was X", "from 93G", "renamed"). That history lives in `docs/name_map.csv` only.
- No hardcoded ROM addresses in comments, and no hand-kept derived counts (sizes, numbers of entries, totals) that the code or the assembler can compute.
- Mark "new in 94" / "new in 95" only for major features, not for every changed routine.
- Local labels in 92 style: `.loop`, `.next`, `.done`, `.exit`, and plain numbers for trivial jumps.
- File headers are short plain-English stories of what the file does, modelled on `hockey93.asm`, `main93.asm` and `menu93.asm`.

Layout (SNES repos, 93S and 94S): `src/banks/` holds ordered bank files named by content (one `org`, then `incsrc` lines in ROM order),
`src/routines/<module>/<Routine>.asm` holds one routine per file, `src/data/<category>/` holds data. The folder is the module of the
routine's origin: 94G for 94 code, else 93G, else 92G; SNES-only code goes in a sensibly named SNES folder. Segment build stubs go in
`src/stubinc`, tools in `tools/`. The build runs a prebuild ROM check that names the path, file name, SHA-1 and size of the ROM it needs
(and extracts the assets automatically where the repo extracts them).

Work in small steps: every change is built and checked byte for byte against the reference ROM, then committed and pushed to main
(no force push, no PRs). Keep `docs/HANDOFF.md` current after each push.

What main is:
- main is a faithful disassembly of the retail game. It keeps only good-practice changes that emit identical bytes: equates and labels instead of hardcoded values, assemble-time checks, and build tooling (the computed checksum and ROM size in `tools/fixrom.js`, `src/shortcalls.inc`, the CHECKSUM/REV flags).
- Mod-specific fixes (long branches instead of the retail short ones, mapper code for save RAM past 2 MB) do not go on main. They are documented in `docs/EXPANDING_THE_ROM.md` or live on mod branches.
- `NumTeams` / `NumPlayoffTeams` and the per-team length checks stay.

## Current segment

None. Every ROM map row is matched, and the full build (`npm run build:retail`) matches `lst/nhl95.bin` byte for byte (SHA-1 09e87b076aa4cd6f057a1d65bb50fd889b509b44). A name another file uses for an address inside a segment must be a label in that segment (PeriodOver_sp $9D18 in hockey95, SeasonScheduleEnd $9721 in schedule95, StickHandTable $83C9E in players95, DrawFaceoffWindow $88E42 in faceoff95); the stub equates only cover the segment build.

RAM (`ram95`) is not a queue segment. It has no ROM bytes, so there is nothing to byte-verify, and the queue moves past its row. RAM names, Z80 RAM and the save RAM offsets (`SR...`) are all in `src/ram95.asm`, which the full build and every stub include. Define each name once, there.

The first split came from the fingerprint map `tools/segmap95.json` (every 94 routine located in `lst/nhl95.bin`); each row's range was then confirmed from the 95 listing as it matched. Routines the ROM map lists as moved in stay in the row's file with a comment naming their 94 file. Keep the includes in ROM order.

## Layout

- One file per 95 subsystem, named for what it does, each one contiguous range of the ROM. The trunk (`main95`, `teamdata95`, `frames95`, `schedule95`, `sram95`, `sound95`, `hockey95`, `display95`, `control95`, `graphics95`, `credits95`, `checksum95`) is in `src/`; the rest is in `sound\`, `engine\` and `front\`.
- `src/nhl95.asm` includes the trunk files and two include lists in ROM order: `engine95.asm`, `front95.asm`. A list names the files of its folder in ROM order. A file lives in its subsystem's folder but is included where its bytes are: `sound\z80old95.asm` is between `fourway95` and `pause95`, so `engine95.asm` includes it. `engine95.asm` is one assembly (PC-relative branches cross every file in it); do not cut it into separate builds.
- The header names the 94 files the file was adapted from. Where a file takes code from more than one 94 file, a `;----` banner before each run gives its address and 94 file (replay94 updateanim in display95, title94 TeamLogoPalettes in graphics95, hockey94 Pausemode in pause95, assign94 in logic95, input94 doinput_cbut in skate95, the title94 shootout paths in shootout95). `docs/FILE_ORIGINS.md` gives the 94 file of every routine.
- Every segment stub is in `src/stubinc/` (`src/stubinc/logic95_stub.asm`). Paths in a stub or a file are relative to `src/` (`include engine\logic95.asm`).
- Sega's cartridge header and power-on code are `src/sega/SegaIDTable95.asm` and `src/sega/SegaInit.asm`, included by `main95.asm`.
- Every label's IDA name, and its old name when it was renamed, is in `docs/name_map.csv`.

## Sources

- Listing: `lst/nhl95.bin.lst`. Open it. Do not disassemble `lst/nhl95.bin`. Do not write a disassembler.
- The listing is an IDA LST in ASM68K / MRI mode. It has no address column. A `loc_`, `sub_`, or `unk_` name is the address.
- Style source: the matching file in https://github.com/abdulahmad/NHL94Genesis. Use https://github.com/abdulahmad/NHLPA93Genesis only when 94 does not have the routine. A 94 name wins when the body is the same routine.
- Reference ROM: `lst/nhl95.bin`. It is 2 MB. Bytes and branch displacements come from it.
- `src/nhl95.asm` and its include lists (`engine95.asm`, `front95.asm`) are in 95 ROM order. Each include line has the file's start address and what is in it.
- Stub includes: `macros\genesis.mac` when the segment uses a macro, `stubinc\ports.inc`, `stubinc\equals.inc`, `ram95.asm`, then the segment file. Outside addresses the segment uses are equates in the stub.

## Teams

Provisional until the listing confirms it. NHL 95 is the 1994-95 season, still 26 teams. Quebec and Winnipeg are still there. Colorado and Phoenix are NHL 96. A 94 team index is not a 95 index until the listing confirms the order.

## Build

`buildseg.bat <name>` assembles `src/stubinc/<name>_stub.asm` (`buildseg.bat logic95`) to `output/<name>.bin`. The stub carries the org. A file included by `nhl95.asm` or an include list has no org; `nhl95.asm` itself sets `org 0` (without it SNASM writes a short, misaligned bin).

`npm run seg:<name>` (`seg:logic95`) runs buildseg with the path, then `tools/fixopcodes.js` on `output/<name> .lst` and `output/<name>.bin`, then `tools/verifySegment.js`. The assembler listing name has a space before `.lst`.

A MATCH of 0 bytes is a failure. The byte count must be the confirmed range.

After every matched segment, delete `output/obj/nhl95.bin` and `output/modified_nhl95.bin`, run `npm run build:retail`, and compare `output/modified_nhl95.bin` to `lst/nhl95.bin`. The full build assembles `src/nhl95.asm`, so the listing stays `output/obj/nhl95 .lst`. An old output can look like a pass. Only a compare made this session counts.

## Rules

- Write real `cmp`, `cmpi`, and `exg`. `tools/fixopcodes.js` rewrites an EA `cmp.l` only. A real `cmpi.l #imm,d0` stays `0C80`. Do not write a compare as `dc.w`.
- Retail pad bytes win over the listing.
- A `printz` string can hide the next instruction. Write the instruction. Do not label a byte inside a string.
- If IDA splits one instruction into `dc.b` and `ori.b`, write the instruction.
- A 94 name is the field even when the 95 value differs. The equate gets the 95 value. The comment records the 94 value.
- Bit names replace the number. Keep the flag word the retail bytes use.
- `jsr name` only when SNASM emits the same opcode. `jsr (name).l` is `4EB9`. `jsr (name).w` is `4EB8`. `bsr.w` stays `bsr.w`.
- A global label ends local-label scope. A local that another routine or another file calls stays global. SNASM cannot reference another routine's local.
- SNASM symbols are case-insensitive. `setVram` and `setvram` are the same symbol.
- Keep each comment line under 200 characters. A longer line makes SNASM write an empty bin, and verify can then print MATCH for 0 bytes.
- Do not delete an asm file. Edit it in place. The exceptions were merging two contiguous pieces of the same 94 file, and the move to one file per subsystem, which replaced the flat files.
- Data goes in the segment of the code that owns it. Sound data follows the sound driver. Graphics are incbins from `tools/extractAssets95.js`, named for the asset, never for an IDA address. A map reference is `Label+8`. Team palettes are `.pal` incbins.
- A new ROM map row gets its include in `src/nhl95.asm` or the include list of its folder, in ROM order, and its stub next to it, in the same session.
- Do not copy a 94 name onto a 95 address because the low 16 bits match. Do not copy a 94 org.
- RAM names go in `src/ram95.asm` when you first encounter them. Write a RAM immediate as `#(Name-M68K_RAM)` and an in-place save RAM access as `SaveRAM+2*SRname`.

## Naming

Name it in the session that transcribes it. Do not leave a cleanup pass.

- Match a function to the 94 routine when the body is the same. Keep the 94 name. Put the IDA name in one `;IDA:` comment on the definition, not on every line.
- If 94 already uses that name for a different routine, do not steal it. Name the new routine from what it does.
- A structure field is an expression (`SortCords+OldXpos`), not a new global.
- Do not leave `loc_`, `sub_`, `unk_`, `word_`, `byte_`, or `dword_` in code or in `ram95.asm`. A branch target inside a routine is a local label (`.name`).
- Bring over the 94 comment when the routine matches. If there is no comment, add one that says what it does.

## Naming lineage

Naming lineage: 92G (abdulahmad/NHL92Genesis, EA original source) is the root. 93G (abdulahmad/NHLPA93Genesis) follows 92G. 94G follows 93G then 92G. 95G follows 94G, then 93G, then 92G. For a field, constant, bit, sound id, hardware name, macro, routine or RAM variable that an earlier game has, use that game's name (in this order); keep the IDA / older name in the comment.
- Lineage renames (93G names over IDA names): printz2 -> printsmallz, dodmalist, setpersonel, GetNameandAttrib, printscores1, MakeTree, NewTicker3 -> CheckGameTickerStatus and NewTicker3pt2 -> NewTicker3, OptionRNG -> GetRandomUnusedTeam, AddPOStats -> DisplayTeamStatsForPlayoffs, getplayername -> GetPlayerNamePointer, d0toascii -> ConverByteToDigits.

Clash rule: if a routine, data label or RAM variable (RAM matched by usage, not address) is clearly the same as one in the parent game, it must take the parent's name. An existing label in the child that already uses that name was misnamed and is renamed to something accurate (its own parent-game name if it has one, else a descriptive name). Old names are kept only in `docs/name_map.csv`.
- 94G/93G/92G renames applied: see docs/name_map.csv (seed, tmstruct, assfaceoffpl, donothing, Penaltylist, GetPlayerName, chk4lc, VBlank_TitleScreen, scouting routines, setupIceRinkMap, reenergizeteam, PrintTeamData, AttribAdjust, GetPlayerNameWithAttrib, AdvanceStringPtr).
- shotdirmath -> CalcAngleOffset; checksum 92 labels promoted.

## Comment rules
- No disassembler (IDA) references in source comments: no `IDA: loc_xxx`, `IDA name`, `sub_`/`unk_` addresses or `Rev A sub_` style labels.
- No rename history in source comments (no `(was: X)`); every rename goes in `docs/name_map.csv` (old,new,source).
